## **2. Mandatory release gates**

Before declaring the project complete, these five gates must pass.

Gate 1

**Correctness**

- All five planning areas generated.
- Every hard constraint validated.
- Budget within approved limit.
- No incorrect message silently accepted.

  Gate 2

  **Performance**
- Initial run under 120 seconds.
- Every update under 60 seconds.
- Maximum five model calls per update.

  Gate 3

  **Transparency**
- Complete model-call trace.
- Actual model names and token counts.
- Original evidence and rejection explanations.

  Gate 4

  **Update handling**
- New messages processed with the same command.
- Only affected areas recalculated.
- Previous valid state preserved when changes fail validation.

  Gate 5

  **Submission**
- Clean Git status.
- Correct submitted commit hash.
- Repository pushed before 1:25 PM.
- Final plan and full trace saved.

## **3. Important decisions to settle during development**

These points are not fully specified in the official brief, so the system should not invent answers:

1. **Meal headcount:** The number of people requiring meals must be established from messages. Do not automatically assume 180 or 177 for the actual event.
2. **Venue generator:** Hall B and Hall C have confirmed standby generators; whether a generator is mandatory depends on the messages and applicable rules.
3. **Food selection:** Standard and basic meal prices are available, but the preferred meal type must be established.
4. **DJ:** The Rs 50,000 request is a proposal, not an approved expense.
5. **Judge lateness:** One judge may arrive 10 minutes late; the system should retain a contingency rather than assume the delay is certain.
6. **Approval authority:** Configure who can approve event-wide changes, financial expenditure and operational decisions. Do not assume every sender has universal authority.

## **4. Definition of complete**

The project is complete when:

- The entire checklist is finished.
- All five planning areas work together.
- The official sample pack passes.
- The two practice updates behave correctly.
- The system catches the plausible but wrong message.
- An unseen message pack can be processed without manually editing code.
- The plan, trace and rejected messages are available in the interface and exported files.
- All runtime and model-call limits are respected.
- All three team members can explain the architecture.

**My recommendation:** Follow the 21 phases in order, starting with project initialization and message ingestion. Do not begin polishing the dashboard until the extraction, conflict engine and planning calculations are working reliably.
